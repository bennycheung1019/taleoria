# Token 使用檢視與建議（2026-10-31）

以下是第 11 版世界的實測，以及尚未實作的新預算架構。計數使用本機 KoboldCpp tokenizer；診斷沒有呼叫文字生成或寫入故事。各部分獨立量度，受模板與分詞邊界影響，不宜當成完全可相加的帳單。

## 現況

提問「我問老麥繩索的情況。」只有 8 tokens，初始輸入卻有 10,522 tokens：

| 部分 | 約 tokens |
| --- | ---: |
| RPG OS 規則原文節錄 | 2,266 |
| 主持及輸出指示 | 1,522 |
| 世界、人物、劇情、歷史索引與追蹤資料 | 5,410 |
| 最近四輪對話 | 1,244 |
| 玩家本次輸入 | 8 |

追蹤資料內的欄位變更時間約 790 tokens，回取的兩段較舊對話約 645 tokens。縮減後主持指示降至 836，但最後輸入仍有 7,183，而且已刪去最近對話。輸出預留 1,200、安全預留 128，總需求 8,511，超過 8,192。

「接著呢？」和「我仔細看他指的岩石。」最初分別 9,868、9,871；最後分別降至 6,529、6,532，但也已失去最近完整對話。這說明只把上限提高或繼續刪對話並非適合長期遊玩的方案。

本機生成沒有雲端 API 的逐 token 帳單。長提示仍會佔用推理時間、上下文記憶體；實際速度也受快取、換頁與輸出長度影響，輸入減半不保證延遲減半。

## 建議：從預算內建立工作上下文

| 普通回合的部分 | 目標 tokens |
| --- | ---: |
| 等效精簡主持規則與輸出契約 | 700 |
| 玩家與目前場景 | 700 |
| 本輪互動人物 | 500 |
| 最近一至兩輪對話 | 600 |
| 相關舊記憶 | 250 |
| 本章當下可用的劇情線索 | 150 |
| 玩家輸入示例額度 | 100 |
| **輸入目標** | **3,000** |

玩家輸入額度應可伸縮，不截斷玩家原句。普通回合以輸入 2,500–3,500 為目標，複雜場景可提升至 4,000–5,000；輸出通常預留約 1,000，需要新人物或劇情建立時再提高。8K 是容納峰值的容量，不是每輪填滿的目標。

1. 將規則整理成經測試的短執行版。保留 RPG OS 原文，只有需要某項細則時取回相關段落；不可只刪掉規則文字而不驗證行為。
2. 對資料種類分配獨立預算。先保留當前行動、最近對話、相關人物及既定後果；欄位時間追蹤改用精簡事件／變更索引，避免逐路徑重複 JSON。
3. 世界完整資料與模型工作記憶分開。地點、人物、承諾、死亡、能力來源等留在資料庫；每輪只載入當下需要的部分。不刪原始日誌。
4. 舊記憶以事件 ID、人物 ID、主題及相關性取回，設 token 上限；不能只因提及姓名就固定塞兩段長舊對話。近期對話優先於低相關舊回憶。
5. 普通交談不每次載入未來章節與全部秘密。只取本章目前可用的依據；探索或章節變化時才增加劇情資料。
6. 同一次 GM 生成回傳必要狀態差異，避免整份人物檔重寫。場景結束或累積一段新事件後才整理較長記憶，避免每輪新增一個摘要模型請求。
7. 將固定指示放在穩定前綴，方便後端重用提示快取；快取不會提高上下文容量。
8. 記錄每輪各類 token、實際輸出及回取內容，讓超額原因可見；預算不足時先移除重複及低相關資料，而非先丟掉最近對話。
